# SDL v2 — persistence, recovery, costs, and metadata scope

**Status: active v2 D06 design.** This extends [Foundations](FOUNDATIONS.md), [Ownership and Bindings](OWNERSHIP-BINDINGS.md), and [Domain Metadata](DOMAIN-METADATA.md). It defines portable declarations and their consistency checks, independently of package support or live infrastructure feasibility. [Cases](conformance/scope-operations.yaml) and a [worked example](examples/scope-operations.sdl.yaml) accompany the rules. Existing v1.1 acceptance and meaning are preserved.

All new records are closed except `x-*`; optional fields remain absent unless authored. A nonblank string contains at least one character other than ASCII space, tab, carriage return, or line feed. Identifiers use ID-001, booleans and numbers are not coerced, and durations use SC-001 with the bounds below. References are checked after composition. Nothing here provisions resources, validates actual prices, verifies recovery tests, or determines legal applicability.

## Database-free and storage-only systems

**SO-001 — Database intent.** The full document retains the `data` root section, but `data.primaryDatabase` is no longer required. Optional `data.databaseMode` is `none | declared`. `none` forbids a primary database and nonempty secondary database list. `declared` requires at least one primary or secondary database. Omission, including `data: {}`, leaves database completeness unspecified; it is not a statement that the system has no databases. Secondary-only configurations are valid and do not fabricate a primary database.

Every declared database still requires its OB-005 ID and existing type/hosting fields. `databaseMode: none` also forbids authored backend-project `orm` fields. A missing ORM is valid and never defaults to one without a database. Existing database references and `dataAccess` must still resolve, so they cannot name a nonexistent database under `none`. Domain entities may describe logical/in-memory records without database bindings and still follow the domain key/type rules. Storage, caches, queues, search, and external integrations can exist without a database; this mode does not assert that those facilities are stateless or free of durable data.

**SO-002 — Storage identities and resource scope.** Each authored `data.storage.blobs` or `.files` declaration requires `id` and `provider`; provider retains the existing four-value vocabulary (`azure-blob`, `s3`, `gcs`, `cloudflare-r2`). Optional `owner` references a team; existing `blobs.public` remains an optional boolean. Storage IDs are unique across both slots. Database IDs and storage IDs are separate namespaces. An empty `data.storage: {}` declares no storage resource; an empty slot object is an incomplete declaration. Each slot declares one logical resource, not a provider account or all buckets of that provider.

A resource reference is exactly `database/<database ID>` or `storage/<storage ID>`. IDs are resolved in their own namespace. Caches, queues, search services, and externally managed integration resources are not silently included in this resource catalogue or its recovery-coverage claims. Their own durability/recovery details require an explicitly identified extension/profile. `databaseMode: none` with a storage resource is a valid storage-only design.

## Environment data instances

**SO-003 — Declared topology.** An environment may declare `dataInstances`, an array of records requiring `name`, `resource`, `target`, and `role: primary | replica`. Optional `replicatesFrom` is an instance name and `maxLag` is a nonnegative duration. Instance names are unique within an environment. Resource and hosting target references must resolve. Each represented resource has exactly one primary instance per environment. A primary forbids `replicatesFrom` and `maxLag`. A replica requires `replicatesFrom` naming the same resource's primary in that environment; `maxLag` is optional and otherwise unspecified. Chains, cross-environment replication, and multi-primary topology are outside this portable model. Reusing instance names or the same logical resource in different environments is allowed.

Referenced targets participate in OB-011's authored region policy and CloudFormation constraint, just like project-placement targets. Multiple data instances may deliberately share a target. A resource instance declares intended hosting and replication relationships, not a connection string, physical endpoint, automatic failover procedure, or proof of provider capability. Database `hosting` remains descriptive; a target may represent a managed service's hosting namespace.

When an environment authors `dataInstances`, every database named in `dataAccess` by its selected projects or selected services must have a primary instance in that environment. This includes an external service's explicitly declared database access. Missing `dataInstances` leaves topology/coverage unspecified; an empty array is an explicit empty model and fails if selected components require databases. Unused logical resources need not appear in every environment. Storage instances are selected explicitly; no storage access is inferred from project names. An omitted topology is never reported as complete.

## Recovery plans and coverage

**SO-004 — Recovery plan records.** `backupDr` has optional `plans`, an array of records requiring identifier `name`, `environment`, `resource`, and `method: periodic | continuous | none`. Names are globally unique in `plans`; each `(environment, resource)` pair occurs at most once. The environment must author a matching primary data instance. A plan covers that resource in that environment, including its declared replicas, rather than backing up every replica separately. Merely declaring a replica is not a recovery plan.

Periodic and continuous plans require nonnegative duration `rto` and `rpo`, positive duration `retention`, and a `destination` hosting-target reference. A periodic plan additionally requires positive duration `interval`; continuous plans forbid `interval`. Periodic `interval` must not exceed `retention` or `rpo`: this periodic-only declaration cannot justify a smaller maximum data-loss window. Continuous plans assert the authored RPO without proving that it is achievable. RTO is the maximum intended restoration duration and RPO the maximum intended loss window; zero is an explicit objective, not evidence of zero downtime or loss. Destination targets participate in the same region/IaC checks as data-instance targets. The same source/destination target is allowed; independence of failure domains is not inferred.

A `method: none` plan requires a nonblank string `reason` and forbids `rto`, `rpo`, `retention`, `destination`, and `interval`. It is an explicit exception to protection, not a zero-valued backup. Protected plans forbid `reason`; both forms permit optional descriptive `notes`. A declared `maxLag` is a replication-lag objective and neither supplies an RPO nor proves recovery coverage. Recovery runbooks and automatic failover execution remain extension/profile details.

**SO-005 — Coverage claims.** Omitted `backupDr.plans` makes no recovery-coverage claim. An authored plans array, including `[]`, requires exactly one plan or explicit `none` exception for every primary resource instance in every environment that authors `dataInstances`. No orphan plan is allowed. Environments without `dataInstances` remain outside that claim; successful validation must not describe them as protected or their resource catalogue as known empty. A plans array with no modeled instances may be empty. Coverage means a declaration exists, not that a backup or restore has succeeded.

**SO-006 — Global backup requirements.** `nonFunctional.backup.frequency`, `.retention`, and `.pointInTimeRecovery` retain their existing names. Frequency `hourly`, `daily`, and `weekly` sets a maximum periodic interval of 1 hour, 1 day, and 1 week respectively; retention is a positive SC-001 duration and sets a minimum retained window. `pointInTimeRecovery: true` requires continuous plans; false states no point-in-time requirement and does not prohibit continuous protection.

If at least one of these fields is authored, `backupDr.plans` is required, every declared environment must author `dataInstances`, and at least one primary resource instance must exist. Every plan must be protected and satisfy the requirements: `none` exceptions are then contradictions. Continuous plans satisfy any frequency requirement; their retention still must meet the authored minimum. Per-plan values may be stricter than global requirements, never weaker. There is no field inheritance or silent overwrite. `nonFunctional.backup: {}` imposes no backup requirement. These global requirements cover only SO-002 resource kinds; they do not certify the recovery posture of caches, queues, or external services.

## Authored cost scenarios

**SO-007 — Cost catalogue.** `costs` has optional arrays `scenarios` and `comparisons`. A scenario requires identifier `name`, `currency`, `period: month | year`, and `items`; optional `environment` references a declared environment. Optional `total` and `budget` are money amounts; optional `assumptions` is an array of nonblank strings. Scenario names are globally unique. Currency is an exact uppercase three-letter accounting label (`^[A-Z]{3}$`); portable validation neither checks an external currency registry nor performs currency conversion. Period denotes the author's reporting period; a month is not treated as 30 days or a year as an automatic 12× conversion. Assumptions should identify pricing dates, billing periods, usage, taxes, and inclusions relevant to interpretation; SDL supplies no market prices.

Each item requires identifier `name`, `subject`, and `amount`; optional `description` is a string. Item names are unique within their scenario. `subject` is tagged by `kind`: `component`, `resource`, and `integration` require `ref` in the component, SO-002 resource, and OB-006 integration namespace respectively; `solution` forbids `ref`. All references must resolve. An environment-specific scenario can estimate planned/unplaced resources; its environment does not claim deployment coverage. Items are separate charges and all contribute, even when subjects repeat. No project/service attribution heuristic deduplicates them. Currency and period are supplied once by the scenario and cannot be overridden by an item.

**SO-008 — Amounts and totals.** Money amounts are nonnegative decimal strings matching `^(0|[1-9][0-9]*)(\.[0-9]+)?$`. Interpret them exactly; reject signs, exponent notation, currency symbols, numeric YAML values, and negative credits. Each item's amount is its entire charge for that scenario period, not a unit rate to be multiplied by inferred usage. Usage/rate detail may be recorded in assumptions/extensions but cannot change the portable arithmetic.

The derived total is the exact sum of all item amounts; empty items sum to zero. Authored `total`, if present, must equal that sum or the scenario is invalid. Omitted total is not inserted into the normalized document. If `budget` is present and the total is strictly greater, emit advisory `cost-budget-exceeded`; equality emits none. Neither `constraints.budget` tiers nor framework/cloud defaults provide a numeric budget or estimate for this check. The estimate remains as complete or incomplete as the author's listed charges.

**SO-009 — Scenario comparisons.** Each comparison requires identifier `name`, `low`, and `high`; comparison names are globally unique. The two references must resolve to distinct scenarios with identical currency, period, and environment (including both absent). Their names alone do not establish comparability. Derived low total must be less than or equal to derived high total; reversing the totals is a declaration error. Emit `high-cost-variance` exactly when `high > 10 × low`, using exact arithmetic. Equality at 10× is not a warning; zero/zero is not a warning and zero/positive is. No division or inferred exchange/period conversion occurs. A comparison is the author's explicit choice of estimate scope; no comparisons are inferred from scenario names, stages, or environment counts.

## Compliance and intentionally open metadata

**SO-010 — Declared compliance applicability.** NM-001/NM-002 still define names, aliases, duplicate detection, and shorthand conversion. A framework's optional `applicable` boolean is an author assessment: true means applicable, false means assessed as not applicable, and omission means unspecified. It does not prove certification or establish a legal obligation from project stage, region, data type, or framework name.

Within each framework, `requirements` is an optional array of records requiring nonblank string `requirement`, unique by exact string within that framework. Optional `description` and `implementation` are strings. Requirements are closed except `x-*`; framework `notes` remains optional descriptive text. Emit `compliance-mapping-missing` for an applicable framework with no requirements, or for each listed requirement whose implementation is absent or blank. Blank uses the string rule above; requirement identifiers themselves must be nonblank and have no leading/trailing ASCII space or control characters. An implementation string records a claimed mapping, not verified effectiveness. Requirements may remain documented for false/unspecified frameworks without triggering this advisory. Assess applicability after NM-002 conversion so shorthand declarations have the same effective treatment as their canonical result.

**SO-011 — Open objects and optional advice.** `design` remains an intentionally open mapping, including `{}`. No token names, framework, component library, or color values are mandatory. Input-profile restrictions still apply to every nested value. `compliance.certifications`, `.dataResidency`, and `.dataRetention` retain arrays of open mapping records; their contents are preserved without portable certification, residency, retention, or resource-binding predicates. They cannot override the typed applicability/requirement rules or resource/recovery definitions.

The portable core emits no stage-derived missing-design or required-compliance-framework warning, and it does not infer cost estimates or budget ceilings from stage/tier. Those historical heuristic warnings require a separately selected, named advisory profile with its own assumptions. This document does not introduce a root profile-selection field or require such a profile for conformance. Other already defined advisories remain unaffected. `costs` and `backupDr` now have the typed shapes above; arbitrary historical content in them must be migrated deliberately to standard fields or `x-*`, rather than treated as silently validated estimates/protection.

## Composition and completion boundary

**SO-012 — Identity, assembly, and normalization.** Data-instance names are unique per environment; storage IDs across the two slots; plan/scenario/comparison names across their respective arrays; cost item names per scenario; requirement names per framework; and plan environment/resource pairs across all plans. Check complete array records and present-field types/enums/grammars locally under ST-001/ST-002, and cross-record references, collisions, coverage, bounds, totals, and policy contradictions after composition. Ordinary object fields, including a storage slot's required members, may assemble across sources. Database IDs still follow OB-005.

New record arrays concatenate under IM-004; none is an identity-replacement registration. In particular, adding a second same-name environment does not patch its instances; it is an environment identity error. Normalization preserves declarations, explicit zero/false/empty values, money/duration spellings, and open metadata except the established NM-002 compliance conversion. It does not invent databases, topology, plans, destinations, applicability assessments, monetary totals, budgets, or defaults. Derived values and coverage boundaries must remain distinguishable from authored facts.

SO-001–SO-010 and SO-012 define errors where their explicit structural/reference/cross-field predicates fail. The cost-budget, high-variance, and compliance-mapping findings are nonblocking advisories under their respective rules. SO-011 specifies preservation and excludes unselected heuristic advice. Diagnostics use CF-001 rule/source/path conventions. An error in a declaration and an advisory about an otherwise valid estimate or incomplete mapping are different outcomes.

| v1.1 scope/gap | v2 decision | Migration requirement |
|---|---|---|
| Required primary database | Optional primary; explicit database intent and valid secondary-only/storage-only designs | Remove placeholder databases/ORMs deliberately and update references; omission alone does not assert no database |
| Unidentified storage and unmodeled data topology | Storage IDs, environment instances, explicit primary/replica relationships | Assign stable identities/targets; no source names or providers are used as identity fallbacks |
| Open recovery metadata and overlapping backup fields | Typed per-environment resource plans and global minimum requirements | Identify actual covered resources, durations, destinations, and exceptions; resolve weaker per-plan settings |
| Open costs and heuristic totals | Exact authored amounts, subjects, scenarios, explicit comparable low/high estimates | State currency/period, convert known values explicitly, and reconcile totals; no inferred pricing or exchange rates |
| Unclear applicability and stage advice | Author assessments, mapping-gap advice, deliberately open metadata | Review applicability and missing mappings; choose heuristic profiles separately if desired |

The selected D06 portable scope is defined. Physical provider capabilities, live recovery proof, detailed runbooks, alternate replication topologies, ecosystem-specific resource durability, price acquisition, legal/certification verification, and optional heuristic profiles are outside this core. [Normalization](NORMALIZATION.md) defines D04, [full-document consolidation](FULL-SPEC.md) and [diagnostic serialization](DIAGNOSTICS.md) define D08, and [release migration](RELEASE-MIGRATION.md) defines D07.
