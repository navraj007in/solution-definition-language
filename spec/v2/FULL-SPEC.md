# SDL v2 consolidated document contract

**Active for the 2.x line; v1.1 is unchanged.** This document brings the v2 slices into one portable document contract. [Release Baselines and Migration](RELEASE-MIGRATION.md) defines the exact baseline and v1.1 migration contract. It does not assert package support.

## Authority and complete structure

**FD-001 — Structural catalogue.** [sdl-v2.schema.json](sdl-v2.schema.json) defines the full authored-document structure using [JSON Schema Draft-07](https://json-schema.org/draft-07/draft-handrews-json-schema-validation-01). It contains every standard field, primitive type, required member, enum, and closed/open object boundary, with only local definition references. The [field catalogue](FIELD-CATALOGUE.md) is a mechanically checked readable rendering. No v1.1 schema, TypeScript declaration, generator, or package default supplies an implicit v2 field definition.

The schema and normative prose together define the contract. The schema handles structural predicates; the prose adds exact scalar interpretation, source-stage rules, identity/reference predicates, and normalization. Passing JSON Schema alone is not SDL conformance. A schema/prose contradiction is a specification defect to fix, not permission to select the more permissive interpretation. Schema validators must disable coercion, default insertion, and removal of unknown properties. Inputs whose exact values cannot be represented fail under IN-005 before an approximate schema evaluation can claim success.

Objects are closed except their declared `x-*` members unless explicitly open in the schema. `design` and the three compliance evidence record arrays are intentionally open under SO-011. Domain `default` and `enum` values and unknown extension values are arbitrary input-profile values, subsequently constrained where the prose says so. An optional field may be absent; it cannot be null unless its schema allows null. A descriptive string may be empty unless its field has a nonempty/nonblank restriction. JSON Schema annotations do not create values. There are no schema default annotations.

Fragment checking follows ST-001/ST-002, not an unconditional application of the full root schema to every module: validate all authored values locally, defer ordinary object requiredness and cross-field predicates to assembly, and require complete declarations inside arrays. Schema `if`/`then`, `dependencies`, and container-level alternatives expressing multiple-field constraints are evaluated after assembly; alternatives describing array-item tagged record shapes must already hold for each complete item. An `x-*` field cannot supply a missing standard field.

## Requiredness and architecture scope

**FD-002 — Document minimum.** A full document requires `sdlVersion: "2.0"`, `solution`, `architecture`, and `data`. Solution requires `name`, `description`, and `stage`. Architecture requires `style` and at least one component across its project categories and services. `projects` itself is optional; services-only architectures are valid. `microservices` additionally requires at least two service declarations, including external services; project count cannot substitute for service count. Other styles impose no further component count or exclusive project/service arrangement.

`data: {}` is valid unspecified persistence; SO-001 defines stronger database intent. `nonFunctional` is optional and, when present, may be `{}`. Availability/scaling objectives are independently optional; an authored availability object requires its `target`. No stage-derived objective is required or inserted. All other unconditional requiredness and list lower bounds are exactly those in the catalogue. Conditional semantic requirements still apply, such as a provider for OIDC, source paths for placements, and recovery coverage for authored backup requirements.

Empty arrays remain explicit empty collections unless a declared bound or coverage predicate rejects them. Array ordering is preserved. No generic uniqueness rule applies to arbitrary lists: identity/reference rules name the lists they constrain. Repeating a descriptive string is legal. Shared-library descriptions alone do not satisfy the component minimum or add deployable units.

## Remaining cross-field predicates

**FD-003 — Security and ORM compatibility.** If `nonFunctional.security.pii` is true, `encryptionAtRest` must be explicitly true in the assembled security object. False or omission rejects. This is an authored design requirement, not evidence that encryption is implemented; `phi`, `pci`, stage, or region does not infer legal applicability or insert security flags.

For each backend project with `orm: ef-core`, inspect its explicit `dataAccess` references. If any resolves to a MongoDB database, reject that project's declaration. An absent/empty access list establishes no database/ORM pair and emits no compatibility conclusion. A MongoDB database used only by a different project is not a conflict. There is no implicit binding to `data.primaryDatabase`. SO-001 independently rejects every authored backend ORM under `databaseMode: none`. Other ORM/database/framework support checks require a separately identified capability profile; the core does not certify those combinations. This replaces the old global primary-database predicate with the explicit v2 access model.

Team-size and scaling counts are nonnegative integers; test coverage targets are integer percentages from 0 through 100 inclusive. These structural bounds do not estimate work, infer headcount, or measure coverage. Other security/session/cache/observability flags are author intent; no additional combinations are rejected beyond the published schema and named semantic rules. For example, `enforce: true` without a coverage target requests enforcement with an unspecified threshold; a tooling profile must resolve that threshold before executing a gate.

## Meanings of retained descriptive fields

**FD-004 — Intent and interpretation.** The following definitions cover the fields not given more specific semantics by the other slices. They are author declarations, never executable instructions to an SDL processor. Absence means unspecified unless ND-004 explicitly gives an effective meaning. Explicit false, zero, empty text, and empty collections retain their authored values.

| Field family | Meaning and boundary |
|---|---|
| `solution.name`, `.description`, `.domain`, `.stage` | Human solution identity, purpose, domain-name label (syntax only; no DNS validation), and planned maturity stage. Name uses the display-name grammar. Stage is a classification, not an assertion of operational quality. Regions and teams use OB-001/OB-011. |
| `solution.repository.org`, `.naming` | Repository organization and naming convention text; no repository is created, discovered, or renamed by validation. |
| `product.personas`, `.coreFlows`, `.valueProposition` | Intended audiences with name/goals and optional access level; ordered user-flow descriptions with name/steps/priority; intended value. Persona access levels describe an audience, not authenticated roles, teams, or authorization bindings. |
| Project `type`, framework/language, runtime version | Optional implementation role within its category; selected framework and primary language under OB-003; an opaque SDK/runtime version string. Category membership does not insert `type`. Version parsing and tool availability belong to capability profiles. |
| Frontend rendering, state management, styling | Selected rendering mode, state library/pattern, and styling approach. Enum membership identifies the intended technique; it does not certify the framework combination. |
| Backend API style/versioning and ORM | Intended transport family, version selection mechanism, and persistence tool. They do not declare API inventory entries, routes, or database access. FD-003 is the portable ORM exclusion. |
| Mobile platform/framework | Target platform classification and implementation framework; no implicit platform/version/distribution matrix. OB-003 still constrains an authored primary language. |
| Service kind, responsibilities, exposes | Logical role, responsibility descriptions, and exposure intent. HTTP base path is descriptive; `openapi`, `grpc`, and `graphql` flags declare intended exposure/documentation. They do not create contracts, ports, or implementation bindings. |
| `architecture.sharedLibraries` | Descriptive name/language records. Neither field creates an identity namespace, dependency target, source path, or a component. |
| Auth roles, sessions, MFA, social providers | Application-role labels; access-token representation, refresh-token use, and TTL objectives; MFA intent and selected social-provider labels. Roles are not team references. TTLs use SC-001, and strategy/provider requirements use OB-006. No session or identity is created. |
| Database type, hosting, name, size, role | Logical engine, management mode, optional physical-name label, qualitative size, and logical purpose. The legacy `role` enum does not create a replica or override the separate SO-003 instance role. |
| Cache, queues, search | Provider/type and intended uses; cache `required` records a requirement, not deployment evidence. Type/provider labels and `none` are preserved. Durability and physical capacity remain outside the SO-002 resource catalogue. |
| Integrations | Provider choices and usage metadata. Payments mode/currency describe payment intent; currency is not inherited by cost scenarios. Custom authentication/rate-limit text does not define executable credentials or SC-001 timing/count rules. Ownership/use references follow OB-006. |
| Availability, scaling, performance | Availability target under SC-002 and descriptive maintenance window; user/concurrency count objectives and descriptive monthly data growth; response/page-load duration objectives. These are targets, not measured service guarantees. No measurement window or load distribution is inferred. |
| Security and backup | Boolean security requirements, audit-logging level and penetration-test intent; FD-003 defines the PII implication. Backup requirements follow SO-006. SDL does not perform audits or security tests. |
| Deployment networking | Public API, WAF, DDoS protection, private-endpoint, and custom-domain intent; no public listener or DNS name is synthesized. |
| CI/CD, infrastructure, environment controls | Selected CI provider, IaC tool and state-backend description; environment automatic-approval/test-gate intent and secret-name labels. No approval, build, deployment, state access, or secret lookup is executed. CloudFormation uses OB-011. |
| Constraints budget/amount/timeline | Budget tier and opaque budget/timeline descriptions. They do not supply numeric values for SO-008/SO-009 or work estimates. |
| Constraints team, existing infrastructure, skills | Declared counts by role; existing-infrastructure description/reuse intent; language skills and cloud experience. Role populations may overlap; `developers` is authored independently, never a sum of other counts. |
| Evolution triggers, roadmap, cost projection | Descriptive conditions/actions/effort/blockers; proposed stages, target-date text, architecture changes and capabilities; narrative costs. These are not executable triggers, parsed dates, commitments, or SO-007 accounting estimates. |
| Feature name, description, priority, stage, status | Flat inventory identity under ID-001/ID-002 and descriptive lifecycle facts. No dependencies, automatic completion, release order, or stage transition is inferred. |
| Testing | Selected unit/E2E frameworks and coverage target/enforcement intent. Coverage is a percentage objective; measurement metric, exclusions, and gate execution require an identified testing profile. Absence does not select a framework or threshold. |
| Observability | Logging provider/structured-output/level, tracing provider/sampling fraction, and metrics provider. Sampling is in [0,1]. No telemetry, collector, sampling default, or backend resource is generated. `none` records no selected provider. |
| Artifact requests | `generate` lists requested output kinds; `formats` chooses supported syntax labels. Requests do not prove a generator exists or an output was produced. Duplicate kinds express one requested kind but stay duplicated in the normalized SDL array. Output file naming and generation are tool contracts. |
| SLOs and resilience | Per-component availability/latency objectives and global resilience configuration. SC-001–SC-004 and EC-008–EC-011 define their numerical and retry meanings; declarations do not measure deployed behavior. |
| Descriptions and `x-*` elsewhere | Descriptive text and preserved extension metadata, constrained only by the input profile unless a named extension profile is explicitly selected. No implicit references or core side effects. |

## Advisory boundary and full conformance

**FD-005 — Core warnings and optional profiles.** Core advisory conditions are exactly those defined in IM-001/IM-004, NM-002, OB-013/OB-014, DX-009, and SO-008–SO-010. Use those rules' applicability and warning kinds. Other heuristics need an explicitly identified optional profile and appear separately under DG-004. In particular, the historical small-team/microservices, timeline estimate, persona/auth, budget-tier, missing-observability, stage/SLO, compliance-stage, and missing-design heuristics are not mandatory v2 warnings. They neither reject a core document nor supply absent facts. Cross-database and unused-integration warnings remain core; numeric costs use only authored SO scenarios.

**FD-006 — Full-document conformance.** A full operation checks the input profile for all sources, local declarations, import graph/composition, final structure, identities/references and all applicable cross-field predicates, ND/NM normalization, and the resulting document's validity. Imports have been removed from the assembled result under IM-004. Canonical debt/compliance representations replace their input aliases; no other omitted architecture fields are inserted. The normalized document satisfies FD-001/FD-002 and semantic predicates. Retain original source lineage, including diagnostics for replaced declarations and removed aliases.

A full success requires every applicable portable rule, including external reference resolution when an API authors `spec`. External-language grammar validation, provider execution/capability validation, runtime retry observations, domain sample-record evaluation, and optional advice are separate scopes. Input-only, structure-only, and slice-only success must never be labeled full-document success. Missing optional plans/objectives remain unknown; full language validity does not certify implementation completeness, deployment safety, or operational maturity.

The [diagnostic contract](DIAGNOSTICS.md) gives a versioned report for outcomes and source locations. [Full-document fixtures](conformance/full-document.yaml) combine the slices and exercise their interaction. The corpus checker verifies packaging and structural expectations; a portable semantic implementation remains later package work.
