# SDL v2 draft — external contracts and error policies

**Status: unreleased selected design for D05 and the retry portion of D04.** This document extends [Foundations](FOUNDATIONS.md) and [Ownership and Bindings](OWNERSHIP-BINDINGS.md). It does not change SDL v1.1 or assert package support. [Expected-result cases](conformance/contracts.yaml) cover these definitions.

SDL inventories APIs and declares shared architectural policy. Operations, request/response schemas, protocol-specific errors, and operation replay guarantees remain in external contracts. The portable checks below establish reference resolution and SDL policy consistency; they do not certify an external document against its ecosystem specification or a running service against either document.

## External contract references

**EC-001 — Reference record.** An API inventory entry may have `spec`, an object with required string fields `path`, `format`, and `version`, and optional string `pointer`. `format` is `openapi`, `asyncapi`, `graphql`, or `protobuf`. `version` is a nonempty, case-sensitive external specification/language version identifier with no leading/trailing ASCII space or control characters; it is not an API product version, file digest, or SDL version. No version is inferred. When `spec` is present, API `type` is required and must match this table. Inventory entries without `spec` remain valid. All records defined here are closed except `x-*`; unknown extensions do not supply missing standard fields.

| API `type` | `spec.format` | Portable handling |
|---|---|---|
| `rest`, `webhook` | `openapi` | Select a mapping whose `openapi` string equals `spec.version` |
| `asyncapi` | `asyncapi` | Select a mapping whose `asyncapi` string equals `spec.version` |
| `graphql` | `graphql` | Whole UTF-8 source file; `version` declares the external language profile |
| `grpc` | `protobuf` | Whole UTF-8 source file; `version` declares the external language profile |

For example, `openapi: "3.1.1"` identifies the document format independently of `info.version`. The same distinction applies to AsyncAPI's format marker. Marker matching is exact, not a range or major-version match. See the [OpenAPI document fields](https://spec.openapis.org/oas/v3.1.1.html#openapi-object) and [AsyncAPI document fields](https://www.asyncapi.com/docs/reference/specification/v3.0.0#A2SObject).

GraphQL and Protocol Buffers sources are not YAML and have no SDL-defined embedded marker check. A declared `version` such as `October2021` or `proto3` selects the intended external profile; portable reference acceptance does not verify that declaration against the source grammar. Ecosystem validation must report its own profile and outcome separately, including unsupported versions. These formats retain their own [GraphQL language](https://spec.graphql.org/October2021/) and [Protocol Buffers language](https://protobuf.dev/programming-guides/proto3/) rules. SDL does not maintain an external-version support catalogue.

**EC-002 — Stable path base.** `spec.path` is a file path relative to the directory of the root SDL document, including when authored in an imported module. It is not relative to the declaring module, the shell working directory, or the project source directory. It consists of nonempty slash-separated segments; absolute paths, empty segments, `.`/`..` segments, backslashes, colons, `?`, `#`, NUL, and control characters are forbidden. No URI decoding, environment expansion, extension inference, remote fetching, or fallback search occurs. A literal percent character is part of the filename.

Resolve within the root directory boundary using the canonical-file/symlink rules of IM-002. A symlink escaping that boundary is invalid. An absent file, directory in place of a file, invalid UTF-8, or invalid selected reference rejects the document; an I/O permission failure or exhausted resource limit fails resolution without claiming the document itself is invalid. No partial result is conformant. Read a referenced canonical file once per resolution operation and use the same content for all references to it; external contract files are not SDL import contributions.

A composed document retains the same root base and unchanged reference spelling. Exporting it to a different directory requires relocating the referenced files or explicitly rewriting paths to preserve targets within the new boundary. Reusing a module in a different root intentionally requires its root-relative contract layout. This is a portability constraint, not containing-module rebasing. `x-spec-path` and other historical extensions remain opaque and are never automatically promoted or fetched.

**EC-003 — Selection and validation boundary.** For OpenAPI/AsyncAPI, parse exactly one mapping document with IN-001–IN-005 (JSON is also acceptable when it satisfies that input profile). `pointer`, omitted or `""`, selects the root. Otherwise it uses the decoded string form of [RFC 6901 JSON Pointer](https://www.rfc-editor.org/rfc/rfc6901), beginning with `/`; URI-fragment notation beginning with `#` is forbidden. Decode `~1` then `~0`; other tilde escapes are invalid. Object keys compare exactly. Array indices are canonical nonnegative decimal integers without leading zeros; `-` never selects an existing item. Missing paths or a selected value that is not a mapping reject the reference. The selected mapping must carry the EC-001 format marker; an operation or schema subtree without that marker is not an API specification entry point.

For GraphQL/Protobuf, `pointer` must be absent (even `""` is rejected), and the decoded UTF-8 file must contain at least one non-whitespace character. Their syntax, imports, and symbol resolution are external-profile checks. For structured formats, `$ref`, remote links, and other ecosystem references are likewise not traversed by the SDL resolver. Their presence does not trigger SDL network access or import semantics. Separate external validation must not be reported as completed merely because the SDL reference resolves.

## Applicability and error-envelope catalogue

**EC-004 — Explicit applicability.** API entries may declare `errorConventions: standard | external`; omission leaves applicability unspecified. `external` leaves the API's error model to its external contract and makes no shared-envelope or retry-eligibility claim. `standard` requires `type: rest | webhook`, an OB-004 `component` binding to a project or a service with `implementation.kind: projects`, and an authored `architecture.errorConventions.envelope`. Binding to an external service or a service with unspecified implementation cannot claim `standard`. GraphQL, gRPC, and AsyncAPI errors are not implicitly converted to HTTP envelopes. API owner teams do not decide applicability.

The standard convention applies to application-generated JSON error bodies and their mapped HTTP error responses at that managed API boundary. It does not require replacing infrastructure-generated responses or bodies forbidden by the HTTP method/protocol. Standard APIs must document the shared shape and mappings consistently in any external contract; verifying ecosystem schemas or deployed behavior is a separate external-profile check. Declaring the root convention alone does not opt every API or external dependency into it. Multiple standard APIs share one root convention; per-API overrides are outside this portable design.

**EC-005 — Envelope fields.** `architecture.errorConventions` retains optional `envelope`, `status_mapping`, and `retry_policy`. An envelope requires `kind: object` and `fields`, an array of field records, and may declare `codeField`. Each field requires `name` and `type`; optional `required` and new `nullable` are booleans, and optional `description` is a string. `name` and `codeField` use dotted paths of ID-001 identifiers. Each segment identifies an object member; there are no escapes, wildcards, array indices, or literal-dot member names. Field paths must be unique. The root object is implicit and cannot itself be named by an empty path.

Field `type` is exactly `object`, `array`, `string`, `integer`, `number`, or `boolean`. Integer and number use the exact finite JSON-compatible numeric meanings in DM-002; booleans are not numbers. Objects and arrays are distinct. An array constrains only the outer value to an array; element shapes remain external-contract detail. Each proper path prefix must be an explicitly declared `object` field in the assembled envelope. Declaration order does not matter; missing parents and traversal through arrays/scalars reject the envelope. Domain custom types and constraints are not automatically envelope types or fields.

**EC-006 — Presence and nullability.** `required` and `nullable` each have effective default `false`; omission is preserved in authored values. Requiredness applies when the immediate parent object exists and is non-null. A required child does not make its parent required or non-null. A present field must have its declared type, unless it is null and `nullable: true`. A missing optional field and a present null are different. Undeclared members are allowed at every object level; this is a minimum envelope shape. `fields: []` therefore permits any JSON object. All example payloads are JSON-compatible values, independent of YAML syntax in the SDL declaration.

If `codeField` is authored it must resolve to a declared `string` field that is required and non-nullable, and every ancestor must also be required and non-nullable. This ensures the code can always be located in a standard error body. It need not be named `error.code`; no path is inferred. The root body remains an object even when all declared fields are optional.

**EC-007 — Status mappings.** `status_mapping` is an array of complete records: required `status` (integer 400–599 inclusive) and `code` (ID-001 identifier); optional `retryable` and `retry_after_header` are booleans. Codes are unique across the assembled mapping; duplicate codes reject even when every value agrees. Several different codes may share a status and may have different retryability. There are no wildcard codes or status-family entries. A nonempty mapping requires an envelope with `codeField`; an empty or absent mapping imposes no such requirement.

The code identifies its declared HTTP status. Matching for retry eligibility requires both the exact code and status; there is no fallback based on status alone. A missing/unknown code or mismatched status has no mapped retry eligibility. An undeclared error code is not a conforming mapped response, but does not make the SDL declaration invalid. Omitted `retryable` means unknown, not true; explicit false denies retry eligibility. `retry_after_header: true` requires `retryable: true`. False or omission makes no requirement that a header be present or absent. The narrower error-status range is a deliberate v2 change from v1.1's 100–599 range.

## One retry policy evaluation per logical call

**EC-008 — Policy completeness.** If `resilience.retryPolicy` is present in the assembled document it requires all three members: `maxAttempts`, `backoff`, `initialInterval`. Backoff is `exponential | linear | fixed`. If `architecture.errorConventions.retry_policy` is present it requires `max_attempts`, `backoff`, `base_ms`, `cap_ms`; its backoff is `exponential | linear | constant`. SC-001/SC-003 bounds apply, including `cap_ms >= base_ms`. Even a one-attempt policy must be structurally complete. Empty/partial policy objects are not defaults. Ordinary object members may assemble across modules under ST-002. No cross-location aliases or casing conversions are introduced.

**EC-009 — Eligibility and shared budget.** For a call to a standard API, an automatic retry is eligible only when the observed error matches a mapping with `retryable: true`, the caller has established that replay of this operation is safe, and at least one of the two policy objects exists. Replay safety is an operational/external-contract fact, not implied by an HTTP status, service dependency, header, or attempt count. Unknown safety denies automatic retry. The portable convention makes no automatic-retry authorization for external/unspecified APIs, unmapped transport failures, or other protocols; separately identified operational profiles can define those cases without claiming this convention supplied their eligibility.

Let `E` be error-policy `max_attempts` and `R` be resilience `maxAttempts`. The shared maximum total executions is `min(E, R)` when both exist, the one authored count when only one exists, and 1 when neither exists. After failed execution number `k` (starting at 1), retry only if eligible and `k` is less than that maximum. The count belongs to the whole logical call, survives changing error codes, and never resets between layers. Do not multiply counts or create nested loops. A limit of 1 and a retryable mapping are compatible: the code is eligible but the budget disallows retries. A larger resilience count never overrides `retryable: false`.

The budget is an upper bound, not a promise to execute every attempt. Success, cancellation, an open circuit, loss of replay safety, or a caller's deadline can stop earlier. `resilience.timeout.default` remains a per-attempt timeout; it supplies neither a total-call deadline nor timeout-failure retry eligibility. This policy does not define service-side automatic replay of an incoming request.

**EC-010 — Delay progression.** For the retry after failed execution `k`, define multiplier 1 for `fixed`/`constant`, `k` for `linear`, and `2^(k-1)` for `exponential`. The resilience delay is its exact `initialInterval` in milliseconds times its multiplier. The error delay is `min(cap_ms, base_ms × multiplier)`. If both policies exist, use the greater delay; otherwise use the one policy's delay. An absent policy does not contribute a delay. A zero base remains zero, including exponential progression.

These are minimum delays measured from completion of the failed execution, not start-to-start periods. Error `cap_ms` caps only that policy's generated delay: it does not shorten a longer resilience or server delay. There is no implicit cap on resilience and no implicit jitter distribution. Implementations may wait longer, but must not wait less; finite resource/timer ceilings may stop the call rather than clamp it to an earlier retry. Exact arithmetic must not wrap, overflow, or round a positive delay down to zero.

**EC-011 — Retry-After.** For a matching standard error response with `retry_after_header: true`, the producer must supply one valid `Retry-After` value. Consumers evaluate a valid header on any otherwise eligible standard error, even if its mapping does not require the header. A header never makes an ineligible error eligible. Parse seconds or HTTP-date using [RFC 9110 sections 10.2.3 and 5.6.7](https://httpwg.org/specs/rfc9110.html#field.retry-after); trim only HTTP optional whitespace around a received field value. For a date, use `max(0, headerDate − responseReceivedAt)` in milliseconds. For seconds, multiply the nonnegative decimal integer by 1000. Compare with EC-010's delay and take the greater value.

Missing, malformed, or multiple Retry-After field values contribute no server delay; do not comma-join repeated values. If the mapping requires the header, these conditions also constitute a producer convention violation. They do not make the SDL policy declaration invalid or bypass the caller's replay-safety/budget checks. A past date contributes zero. If a deadline cannot accommodate the required delay, stop the call; do not shorten the delay to fit. The header rule declares no default producer delay or dependency on a client's locally chosen backoff.

## Composition, diagnostics, and migration

**EC-012 — Composition and normalization.** API entries, envelope fields, and status mappings use ordinary array concatenation under IM-004; none is a new identity-replacement collection. Duplicate API names, field paths, and codes are errors within a source and in the assembled result. Required members of those array records, including nested `spec`, must be supplied in the originating source. Missing parent envelope fields, code selectors, policy members, component references, and applicability checks may be satisfied by other sources and are checked after assembly. Path spelling and its root base do not change during merging. Normalization must not infer API type, version, applicability, code paths, mappings, retry policies, or operational replay safety. Effective defaults in EC-006 and budget evaluation are interpretations, not fabricated authored fields.

EC-001–EC-008 and EC-012 define declaration/reference errors; EC-002 also distinguishes failed I/O/resource operations. EC-009–EC-011 define operational interpretation, not rejection of a well-formed policy because a particular call must stop. Scoped cases may include an `observation` or `payload` outside the SDL `value`; these are evaluation inputs, never proposed SDL fields. Diagnostics use CF-001 rule IDs, source identities, and decoded paths. A missing external file identifies both the referring `spec.path` and the attempted root-relative target; pointer/marker failures identify the selector and external source. Full external-format validators report separately scoped diagnostics.

| v1.1 baseline/gap | v2 action | Migration requirement |
|---|---|---|
| Extension-only external pointers | Optional first-class `spec` with explicit type/format/version and root-based local path | Identify the old extension's actual base and target before rewriting; do not copy an unverified module-relative path |
| Implicit global error applicability | Explicit per-API `errorConventions` and managed-component requirement for `standard` | Select applicability; protocols and external services keep their external error models |
| Free-form envelope type/path meaning | Closed type vocabulary, explicit object parents, relative requiredness/nullability, explicit code selector | Repair ambiguous paths/types; preserve intended optional parents and supply code location when mappings exist |
| Broad HTTP status range and unclear identity | Error statuses 400–599, unique codes, multiple codes per status allowed | Move non-error statuses out of error mappings and reconcile duplicate codes |
| Partial resilience policies and undefined precedence | Complete policies, shared minimum count, maximum of independently generated waits, explicit eligibility | Supply intended values and assess changed retry timing/counting; no inferred defaults or multiplied loops |

D05's portable reference and shared HTTP-policy design is defined by this document. Remote reference acquisition, external-language validation profiles, per-operation policy overrides, transport-specific retry classifiers, and wire-protocol adapters remain explicitly outside that design. [Full-document integration](FULL-SPEC.md), [diagnostic serialization](DIAGNOSTICS.md), and [release migration](RELEASE-MIGRATION.md) are now defined; packages can implement the settled definitions later.
